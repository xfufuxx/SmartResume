# 30 passed, 6 warnings in 1.90s

覆盖 5 组：用户封禁/解封（含 admin log 落库）、Prompt 版本与灰度部署（自动激活、递增、灰度比例路由、回滚、按用户解析）、订单退款（成功单/非成功单/超 30 天/不存在/充值退款重置额度）、额度消耗（免费日额度、VIP 不限、日限额触顶、跨日重置、新增额度）、管理员角色与日志字段。

**⚠️ 隐患（不影响通过，但削弱测试有效性）**：运行时报出 6 条 `RuntimeWarning: coroutine 'AsyncMockMixin._execute_mock_call' was never awaited`，出自 `app/services/prompt_service.py:50`（`db.add(prompt)`）与 `app/services/quota_service.py:73`（`db.add(quota)`）。含义是：mock 的 `db` 把 `add` 配成了 `AsyncMock`，而业务代码里 `db.add()` 是**同步**调用 → 产生一个从未被 await 的协程对象。**用例虽然通过，但 `db.add` 实际未产生任何可断言的效果**，即"写库"这一环在这些用例中等于被静默跳过。修复方向：把 mock 的 `db.add` 从 `AsyncMock` 改为 `MagicMock`。

### 4.3 `tests/test_matching.py` —— 5 failed / 9 passed

```bash
.venv/Scripts/python.exe -m pytest tests/test_matching.py -q
# 5 failed, 9 passed
```

| # | 用例 | 断言 | 实际 | 根因（已定位） |
|---|---|---|---|---|
| 1 | `TestMatchCalculator::test_perfect_match` | `match_rate >= 70` | **64** | 用例前提不成立。`app/services/match_calculator.py`: `match_rate = int((keyword_score*0.7 + quant*0.3)*100)`。实测 64 ≈ 全命中没拿到"量化成果"那 0.3 权重（或样例少命中 1 个关键词），故"完美匹配"场景实际没构成完美匹配。 |
| 2 | `TestScoringEngine::test_incomplete_resume_scores_low` | `total_score <= 40` | **41** | 阈值漂移，差 1 分。`scoring_engine.py` 的加权与下限（`max(score, 10)` / `max(score, 30)`）在当前实现下产出 41。 |
| 3 | `TestScoringEngine::test_excessive_experience_points` | `format_readability < 90` | **90** | 边界错误。`scoring_engine.py:133` 规则为 `if len(points) > 8: score -= 10`。用例给 12 条 → `100-10=90`，而断言写死 `< 90`。断言应为 `<= 90`，或算法扣分需大于 10。 |
| 4 | `TestMatchAPI::test_match_endpoint_returns_correct_shape` | 状态码 ∈ {401, 404} | **403** | **产品行为问题**，见下方"403 根因"。 |
| 5 | `TestMatchAPI::test_batch_optimize_validation` | 状态码 ∈ {400, 401, 422} | **403** | 同上。 |

#### 🔴 403 根因（本例最重要的发现，已定位到行）

`backend/app/core/deps.py` 第 13 行：

```python
bearer_scheme = HTTPBearer()
```

FastAPI 的 `HTTPBearer()` **默认 `auto_error=True`**：请求缺少 `Authorization` 头时，它直接在框架层抛 **403 Forbidden**，根本不会走到函数体内的 401 分支（该文件第 76、83 行才 `raise HTTPException(401, ...)`）。

影响：**整个 API 层所有受保护接口，在"未带 token"时都返回 403 而非 401**。这既是这 2 个用例失败的原因，也是一处产品行为缺陷——语义上"未认证"应为 401，"已认证但无权限"才为 403；前端据此做"跳登录页"还是"提示无权限"的区分会判断错误。

修复二选一（需产品侧定夺，属行为变更）：
- **改代码**（推荐）：`HTTPBearer(auto_error=False)`，再在函数体内对 `credentials is None` 显式 `raise HTTPException(401, "未提供认证凭据")`。同时建议补 `WWW-Authenticate: Bearer` 响应头。
- **改测试**：若确认 403 是既定契约，则把断言改为 `in (403, 404)` / `in (400, 403, 422)`。**不推荐**——会掩盖而非解决语义问题。

### 4.4 `tests/test_auth.py` —— 10 个用例**完全无法收集**

```bash
.venv/Scripts/python.exe -m pytest tests/test_auth.py -q
# ERROR tests/test_auth.py - ModuleNotFoundError: No module named 'jwt'
# !!! Interrupted: 1 error during collection !!!
```

**根因（已定位到行）**：

| 位置 | 导入语句 | 库 |
|---|---|---|
| `backend/app/core/security.py:2` | `from jose import jwt` | **python-jose**（在 `requirements.txt` 中） |
| `backend/tests/test_auth.py:9` | `import jwt` | **PyJWT**（**不在任何依赖清单中**） |

两个库**同名不同源**，项目实际用 python-jose 签发/解析 token，测试却 import 了 PyJWT，故 `ModuleNotFoundError`。

更要紧的是：**该文件的收集错误会中断整个 `tests/` 目录的运行**（pytest 默认 `--maxfail` 行为下表现为 `Interrupted`），意味着**只要在 `backend/` 下裸跑 `pytest`，一个 import 错误就让 `test_matching.py`、`test_admin.py` 的 44 个用例一个都跑不了**。

修复方向（推荐第 1 项）：
1. 把 `tests/test_auth.py:9` 的 `import jwt` 改为 `from jose import jwt`（与产品代码对齐）；若其中用到 PyJWT 专有 API 需一并调整。
2. 或者把 PyJWT 加进 `requirements.txt` + CI 安装步骤（治标，两套 JWT 库并存易再踩坑）。
3. 无论选哪种，都建议给该文件加 `pytest.importorskip` 或把外部依赖缺失场景隔离，避免再次"一个文件废掉整个套件"。
