# 智能简历优化系统 · 功能测试流程文档

> 配套《智能简历-功能简介.md》。本文档覆盖全部功能的**详细测试步骤、预期结果**，并重点设计**跨功能关联测试用例**，验证相互关联功能之间的数据流转与交互正常、无冲突或遗漏。
> 执行方式：既可用于接口（curl / Postman / pytest）验收，也可作为 UI 手测脚本。代码为唯一事实来源。

---

## 1. 文档说明

- **目标**：① 逐功能给出可执行测试步骤与预期；② 通过跨功能用例验证端到端数据一致性与交互正确性。
- **范围**：认证、简历、优化、评分、岗位库、匹配、ATS、批量优化、面试押题、导出、首页洞察、搜索、站内消息、投递（含四类通道与回执闭环）、面试进度、沟通消息、面试追踪枢纽、回收站、管理员后台。
- **约定**：
  - 接口前缀统一为 `/api`；鉴权接口用 `Authorization: Bearer <access_token>`。
  - `base` = `http://localhost:8000`，前端 `http://localhost:3000`。
  - 下列用例以 `curl` 示意关键请求，实际可替换为任意测试客户端。

## 2. 测试环境准备

### 2.1 本地启动顺序（不可颠倒）
1. **Redis** `:6379`：`"D:/Redis-x64-3.0.504/redis-server.exe" --port 6379 --dir "D:/Redis-x64-3.0.504"`（缺 `--dir` 会启动失败）。
2. **后端** `:8000`：在 `backend/` 用虚拟环境 `RELOAD=false .venv/Scripts/python.exe run.py`（稳定启动务必 `RELOAD=false`）。
3. **前端** `:3000`：受管 Node 启动 `next dev`（首编译可达 ~90s，探测超时 ≥120s）。

### 2.2 演示账号
- 邮箱 `demo@smart-resume.com` / 密码 `Demo@123456`（回归脚本同款）。
- 需 admin 后台用例时另行准备管理员账号（见 `POST /api/admin/login`）。

### 2.3 dry-run 模式（关键）
- 未配置 SMTP/IMAP（`backend/.env` 中 `SMTP_*`/`IMAP_*` 为空）时，邮件直投与回执同步进入 **dry-run**：接口正常返回、投递事件照常落库，但**不出网**。`email/sync` 直接返回 `{"enabled": false, ...}`。回归与手测均可在 dry-run 下完成主流程。

### 2.4 测试前的清理（避免额度 / 重复约束干扰）
- 跨功能用例一天内多次运行会耗尽 Redis 每日额度（`delivery:count:{user}:{yyyymmdd}`，上限 20）→ 批量 / 邮件断言 429 级联失败。重跑前执行：
  ```
  redis-cli -p 6379 DEL "delivery:count:*"
  ```
- 投递唯一约束：`user_id + job_image_id`。重复投递返回 409，需先 `DELETE /api/applications/{id}` 撤回释放后再投。

## 3. 通用测试约定

### 3.1 常用 HTTP 状态码
| 码 | 含义 |
| --- | --- |
| 200/201 | 成功（201 多为创建） |
| 400 | 参数 / 业务校验失败（如未解析、格式错误） |
| 401 | 未登录 / Token 失效 / 管理员未登录 |
| 403 | 账号冻结 / 签名 URL 失效 |
| 404 | 资源不存在或无权访问（按 `user_id` 过滤后为空） |
| 409 | 冲突（已投递该岗位） |
| 422 | 校验失败（PIPL 未同意 / 邮箱格式 / 退信名单 / 缺公司名） |
| 429 | 当日投递额度用尽 |
| 413 | 文件过大 |
| 500 | 服务器内部错误（如 PDF 生成失败） |

### 3.2 关键枚举值速查（前后端共用，避免漂移）
- **投递状态** `APPLICATION_STATUSES`：`submitted`(已投递) / `viewed`(被查看) / `interview`(邀面试) / `offer`(已录用) / `rejected`(不合适)
- **投递通道** `DELIVERY_CHANNELS`：`email`(邮件直投) / `manual`(手动记录) / `form`(官网表单) / `guide`(平台引导)
- **投递触达状态** `DELIVERY_STATUSES`：`pending`(发送中) / `sent`(已送达) / `failed`(失败) / `bounced`(退信) / `not_applicable`(记录模式)
- **沟通方向** `COMMUNICATION_DIRECTIONS`：`out`(我→公司) / `in`(公司→我)
- **沟通渠道** `COMMUNICATION_CHANNELS`：`phone` / `email` / `wechat` / `other`
- **面试进度状态** `interview_tracks.status`：`scheduled`(待面试) / `awaiting`(待结果) / `passed`(已通过) / `offer`(已获 Offer) / `rejected`(未通过)
- **面试轮次** `stage`：笔试 / 一面 / 二面 / 三面 / 群面 / HR面 / 终面 / 其他
- **面试方式** `mode`：现场 / 线上 / 电话

### 3.3 PIPL 同意规则
- 邮件直投：需 `recipient_email` 非空 **且** `consent_given=true`，否则 422。
- 官网表单：`apply_url` 非空 + `consent_given=true`。
- 平台引导：`channel_hint=guide` **且** `consent_given=true`。
- 手动记录（无对外发送）无需 `consent_given`。

## 4. 单功能测试用例

> 编号说明：`SF-xx`（Single Function）。每个用例含：目标 / 前置 / 步骤 / 预期 / 异常边界。

### 4.1 认证（Auth）
**SF-01 注册并登录**
- 目标：验证邮箱+验证码注册与双 Token 登录。
- 前置：邮箱未被注册；后端可发码（或测试用已知验证码路径）。
- 步骤：
  1. `POST /api/auth/send-code` {email, purpose:"register"}
  2. `POST /api/auth/register` {email, code, password(≥8位), platform?}
  3. `POST /api/auth/login` {email, password} → 保存 `access` / `refresh`
  4. 用 `access` 调 `GET /api/user/profile`
- 预期：② 201 返回 token；③ 200 返回 token；④ 200 返回个人资料。
- 异常：已注册邮箱注册 → 400；密码 <8 位 → 400；验证码错误/过期 → 400。

**SF-02 Token 刷新与设备下线**
- 步骤：`POST /api/auth/refresh` {refresh_token}；`GET /api/auth/devices`；`DELETE /api/auth/devices/{device_id}`；`POST /api/auth/logout`。
- 预期：刷新返回新 `access`；设备列表含当前设备；下线后该设备 Token 失效；退出后 `access` 仍短期有效但 `refresh` 吊销。
- 异常：`refresh` 无效/已吊销 → 401。

**SF-03 忘记密码 / 改密码 / 冻结账号**
- 步骤：`POST /api/auth/forgot-password/send-code`；`reset`；`POST /api/auth/change-password`（需旧密码）；`POST /api/auth/delete-account`（30 天冻结）。
- 预期：各环节返回 200/成功；未注册邮箱发码 → 404；旧密码错误 → 400。

### 4.2 简历管理（Resumes）
**SF-10 上传解析**
- 步骤：`POST /api/resumes/upload`（multipart file，PDF/图片/Word）。
- 预期：201 返回 `id`、解析状态；`raw_text` 加密入库；`GET /api/resumes` 可见；`GET /api/resumes/stats` 计数 +1。
- 异常：类型不支持 → 400 `FILE_TYPE_INVALID`；超 50 页/超大小 → 413 `FILE_TOO_LARGE`；解析失败 → 400 `RESUME_PARSE_FAILED`。

**SF-11 收藏 / 设主 / 复制 / 改名**
- 步骤：`POST /api/resumes/{id}/favorite`（切换）；`PUT /api/resumes/{id}/primary`；`POST /api/resumes` {source_resume_id}；`PUT /api/resumes/{id}` {title}。
- 预期：各返回 200/成功；主简历唯一；复制产生新记录（归属本人）。

**SF-12 回收站与恢复**
- 步骤：`POST /api/resumes/batch-delete` {ids}；`GET /api/resumes/trash`；`POST /api/resumes/{id}/restore` 或 `batch-restore`；`DELETE /api/resumes/{id}`（硬删）。
- 预期：删除后进回收站（列表仍可通过 trash 查到，常规列表不可见）；恢复回到常规列表；硬删后不可见。
- 异常：删不存在 → 404；恢复非回收站条目 → 404。

**SF-13 简历版本树（P0）**
- 前置：存在简历 R，且已对 ≥2 个岗位做过优化，其中一条做过 ≥1 次 refine。
- 步骤：`GET /api/resumes/{R}/version-tree`；前端「简历管理 → 卡片菜单 → 版本树」。
- 预期：200 返回 `root(kind=original)` + 一级 `optimized` 节点（含 `job_title`/`company`/`match_score`/`created_at`）+ 其下 `refined` 链（`parent_record_id` 逐级挂靠，可多级）；`optimized_count`/`refined_count` 与实际一致；按 `created_at` 升序；软删除的优化版不出现在树中。
- 异常：简历不存在或非本人 → 404；无任何优化版 → root.children 为空数组（前端显示引导文案）。
- UI：卡片菜单出现「版本树」；弹窗树形图默认全展开，原始版/优化版（含匹配分 Tag）/微调版（第 N 次修改）三类节点样式正确；顶部显示「N 个岗位优化版 · N 次微调修改」摘要。

### 4.3 简历优化（Optimize）
**SF-20 同步优化**
- 前置：已上传解析的简历 `R` 与岗位 `J`。
- 步骤：`POST /api/optimize` {resume_id:R, job_image_id:J, template:"professional"}。
- 预期：201 生成优化记录；`GET /api/optimize/{id}` 含优化内容；可 `GET /api/export/optimize/{id}/docx` 导出。
- 异常：简历/岗位不存在 → 404；简历未解析 → 400 `PARSE_BEFORE_OPTIMIZE`。

**SF-21 异步优化 + 状态轮询 + 取消**
- 步骤：`POST /api/optimize/async` {resume_id, job_image_id} → 得 `task_id`；`GET /api/optimize/async/{task_id}` 轮询（pending→processing→completed）；`POST /api/optimize/async/{task_id}/cancel`。
- 预期：轮询可观察到状态流转；取消后任务终止；完成后 `optimize` 列表出现记录。
- 异常：查询不存在/过期 task → 404。

**SF-21a 可靠任务队列：悬挂恢复与心跳兜底（P0）**
- 前置：Redis 运行中；后端可重启。
- 步骤与预期（三层保障逐一验证）：
  1. **启动恢复**：向 Redis 写入 `optimize_task:test-*`（status=processing/pending）→ 重启后端 → 查该 key 应变为 `failed`、progress=「服务重启导致任务中断，请重试」；DB 中 `interview_sessions.status=pending` 与 `batch_optimizations.status∈(pending,processing)` 同样在启动时被判 failed（`error_message` 同文案）。
  2. **心跳超时兜底**：写入 status=processing、`updated_at` 为 11 分钟前的任务 → `GET /api/optimize/async/{id}` 应返回 `failed`「任务长时间无进展，已自动判定为失败，请重试」，且 Redis 中已持久化；写入心跳 1 分钟前的同状态任务 → 保持 `processing` 不被误判。
  3. **执行器兜底**：构造一个会抛未捕获异常的后台任务（或代码评审确认 `_spawn_task` done-callback 存在）→ 任务应落 `failed`「任务执行异常（类型），请重试」，日志出现 `[任务执行器] 异常逃逸`。
- 边界：无 `updated_at` 的旧数据不做心跳判定（交由启动恢复）；批量阈值 = max(30 分钟, 3 分钟×岗位数)；恢复函数幂等（重复调用 0 变更）；恢复只动 pending/processing，不碰 completed/failed/cancelled。
- 清理：删除测试用 Redis key；确认版/批次测试数据按各自用例清理。

**SF-22 差异对比 / 在线编辑 / 满意度 / 精炼**
- 步骤：`GET /api/optimize/diff?id1=&id2=`；`PUT /api/optimize/{id}/content`；`POST /api/optimize/{id}/feedback` {rating:1-5}；`POST /api/optimization/{id}/refine` {instruction}（≤3 次）。
- 预期：diff 返回逐段差异；content 更新；feedback 首位 201、重复 409；refine 成功、超 3 次 → 400。

**SF-23 AI 修改逐条确认（P0）**
- 前置：存在优化记录 O（原始 JSON 与优化 JSON 确有内容差异）。
- 步骤：`GET /api/optimize/{O}/changes`；前端「优化完成对比弹窗 → 逐条确认 AI 修改」。
- 预期：
  1. 变更清单为条/点级：summary、skills（细化/新增/移除分开列）、experience（头部字段一项 + 每条描述一项）、projects（整段一项）；每条含稳定 `id`、`kind`（modified/added/removed）、前后文本、`editable` 标记。
  2. 前端逐条接受 / 拒绝；editable 条目接受后出现文本框可改 AI 文案（编辑后接受）；「全部接受 / 全部拒绝」快捷操作正确。
  3. `POST /{O}/changes/apply` 提交决策 → 201 返回新记录：`parent_record_id=O`、`changes_description` 含「接受 N 条 / 拒绝 M 条」；新记录 `optimized_json` = 原始简历 + 仅被接受的变更（编辑文本生效；被拒绝的条目保持**原文**）；原记录 O 完全不变。
  4. 未出现在 decisions 中的变更视为拒绝；全部拒绝 → 400「至少接受一条」；记录不存在/非本人 → 404。
- UI：弹窗按章节分组；接受项底色变化；应用成功提示后主页面右侧「AI 优化后简历」刷新为新版本内容。
- 清理：测试生成的确认版记录移入回收站（trash），不影响其它用例。

**SF-23a AI 事实核验（P0）**
- 前置：同 SF-23（O 的 AI 建议中含数字改写 / 强主张词 / 纯新增内容）。
- 步骤：`GET /api/optimize/{O}/changes`，检查每条 `fact_check` 字段与前端徽标。
- 预期（规则引擎，无 LLM 调用）：
  1. **数字比对**：建议文本中出现而原始简历没有的数字（含 %/倍/万/k/x 单位）→ `added_number` + 前端 ⚠「新增数字：35%」徽标；数字原文已有 → 不标。
  2. **夸大词**：「精通 / 主导 / 资深 / 专家 / 行业领先 / 显著 / 大幅」等强主张词出现在建议中而原文没有 → `exaggeration` + ⚠「可能夸大：词列表」。
  3. **纯新增**（新增描述/简介，原文为空）→ `insufficient_source` + ⚠「原简历未提及此内容」；若其中含数字/夸大词一并标出。
  4. **技能**：真正新增技能 → `added_skill`（⚠ 新增技能，AI 推断）；同源细化（如 微服务→微服务开发）→ `sourced`（✅），不误报。
  5. **有依据**：改写与原文相似度 ≥0.3 且无数字/夸大问题 → `level=ok` + ✅「来源于原始简历」；相似度 <0.3 → `insufficient_source` 警告。
  6. 响应 `warn_count` = 警告条数；前端顶部黄条显示「事实核验提示：N 条建议包含 AI 新增的数字 / 技能 / 强主张表述」。
  7. 移除类变更（`removed`）无事实核验字段（AI 未做新主张，无需确认）。
- UI：徽标渲染在每条建议的标题行下方、修改前后对照上方；ok 徽标绿色，警告徽标橙色（#FFFBE6 黄底警示条）。
- 边界：数字「3年→5年」这类经历年限改写应报 `added_number`（原文 3、建议 5）；同一数字原文已有（如「提升35%」改写自「优化35%」）不报。
- 清理：无数据写入（只读端点）。

### CFT-01 全链路主线（简历→优化→投递→追踪→沟通→导出）

  1. 上传解析 `R`；上传解析 `J`。
  2. `POST /optimize` 生成优化记录 `O`；`GET /resume/{R}/score`、`/match`、`/ats/check` 校验依赖 `parsed_json` 成功。

  3. 从投递记录「记一笔沟通」关联 `A`；在「沟通消息」确认该条 `application_id=A` 且 company/position 自动带出。
- **预期**：枢纽三 Tab 数据同源；状态修改实时反映；沟通关联快照正确。
- **冲突检查**：投递与面试进度是独立数据，改面试进度**不应**反向改写投递状态（避免数据冲突）；沟通关联投递后，投递删除需按 `SET NULL` 处理（见 CFT-05）。

### CFT-03 邮件回执闭环跨模块联动（退信→名单→沟通）
- **涉及**：投递(email) → `email/sync` → 抑制名单 `suppressions` → 沟通 `communications` → 投递记录状态。
- **前置**：配置好 IMAP（或 mock IMAP 返回 1 封退信 + 1 封回复，针对已发邮件的 `provider_message_id`）。
- **步骤**：
  1. 邮件直投 `A`（dry-run 亦可，只要 `provider_message_id` 落库）。
  2. `POST /applications/email/sync` 拉取回执。
  3. 断言：退信 → `A.delivery_status=bounced` 且 `suppressions` 新增该邮箱；回复 → 自动生成 `communications`（`direction=in`, `channel=email`，company/position 来自 `A` 关联岗位）。
  4. 在枢纽「沟通消息」确认该回复可见。
- **预期**：回执驱动三处数据变更（投递状态、抑制名单、沟通记录），且沟通出现在「沟通消息」而非「站内消息」。
- **冲突检查**：同一封邮件按 Message-ID 去重，重复 sync 不产生重复事件/沟通；退信命中后该邮箱后续直投被 422（`is_suppressed` 二次校验）。

### CFT-04 岗位删除级联对投递与追踪的影响
- **涉及**：岗位库 `jobs` → 投递 `applications`（FK CASCADE）↔ 面试进度、沟通（仅快照）。
- **步骤**：
  1. 投递 `J` 得 `A`；新增关联 `A` 的沟通 `C`；新增面试进度 `T`（关联 `J` 的 `job_image_id` 快照）。
  2. `DELETE /api/jobs/{J}`（硬删，触发级联）。
  3. 断言：`GET /applications/check/{J}` 返回 `applied=false`（投递随岗位级联删除）；`GET /applications` 不再含 `A`；但 `GET /communications` 仍含 `C`（内容保留，公司/职位快照不变）；`GET /interview-tracks` 仍含 `T`。
  4. 岗位库重新上传同公司同名岗位 `J2`，在岗位页「已投递」标记应已还原（因 `A` 已随 `J` 删除）。
- **预期**：级联删除只清投递，关联沟通/进度因快照保留不丢失数据；无外键报错。
- **冲突检查**：岗位删除后不应残留「幽灵」投递记录；面试进度/沟通不会因岗位消失而报错。

### CFT-05 投递撤回：约束释放 + 沟通保留
- **涉及**：投递 `applications` ↔ 抑制名单（无）、沟通 `communications`（SET NULL）、唯一约束。
- **步骤**：
  1. 邮件直投 `J` 得 `A`；对其新增沟通 `C`（关联 `A`）。
  2. `DELETE /applications/{A}`（撤回）→ 断言返回 `withdrawal_email`（dry-run 或 sent/failed）。
  3. 断言：`GET /applications/check/{J}` = `applied=false`（唯一约束释放）；`GET /communications/{C}` 仍存在且 `application_id` 变为 `null`，但 company/position/content 不变。
  4. 重新 `POST /applications` 投 `J` → 201 成功（证明约束已释放，可重投）。
- **预期**：撤回释放约束且不丢沟通；撤回告知邮件按通道触发。
- **冲突检查**：撤回后若再对 `A` 做 `PUT/GET/delivery-events` 应 404；沟通不再反向引用已删投递。

### CFT-06 抑制名单双向控制（含批量）
- **涉及**：投递(email) ↔ `suppressions` ↔ 批量投递 `batch`。
- **步骤**：
  1. 手动 `POST /applications/suppressions` {email:E}。
  2. 单投 `J` 填 `recipient_email=E` → 期望 **422**（被拦截）。
  3. 批量投递含 `J`（映射 E）→ 期望该项 **422 跳过**，且 `failed_quota=0`（未消耗额度）。
  4. `DELETE /applications/suppressions/{id}` 移除 E。
  5. 重投同一 `J`+E（先确保未投过，必要时先撤回）→ 期望 **201** 成功且额度 +1。
- **预期**：名单对单投与批量一致生效；移除后可恢复；退信自动加入（CFT-03）与手动加入走同一 `is_suppressed` 判定。
- **冲突检查**：命中名单不消耗每日额度（避免「被拦截却扣额度」的不一致）。

### CFT-07 简历/岗位软删后对引用方的影响
- **涉及**：简历、岗位回收站 ↔ 优化、投递（展示快照）。
- **步骤**：
  1. 上传 `R`、`J`；优化得 `O`；投递 `J` 得 `A`（引用 `R` 与 `J`）。
  2. 将 `R` 移入回收站（`batch-delete`）；`J` 移入回收站。
  3. 断言：`GET /applications/{A}` 仍可返回（展示 applicant 信息快照 + 岗位标题来自 `J` 快照，未报外键错）；`GET /optimize/{O}` 仍可查看。
  4. 恢复 `R`、`J` → 常规列表重新可见，引用方无需改动。
- **预期**：软删后引用方通过快照/查询容错正常展示，无 500。
- **冲突检查**：硬删（`DELETE`）岗位会级联清投递（CFT-04），而软删不触发级联——两者行为必须明确区分，不能混淆。

### CFT-08 站内消息 vs 沟通消息 数据隔离
- **涉及**：`/messages`（系统通知） ↔ `/communications`（投递沟通）。
- **步骤**：
  1. 经 `email/sync` 产生一条 HR 回复 → 断言写入 `communications`（`direction=in`）。
  2. `GET /api/messages` 列表断言**不含**该回复；`GET /api/communications` 含之。
  3. 系统产生一条站内消息（如额度/审核类）→ `GET /messages` 含之，`GET /communications` 不含之。
- **预期**：两套数据完全独立，互不直接写入；前端「站内消息中心」与「面试追踪-沟通消息」各自正确。
- **冲突检查**：不得出现「HR 回复既进沟通又进站内消息」的重复；也不得出现「系统消息误进沟通」。

### CFT-09 全局搜索跨模块聚合
- **涉及**：搜索 ↔ 简历 / 岗位 / 优化。
- **步骤**：
  1. 准备：简历含关键词 `K`、岗位含 `K`、优化记录含 `K`。
  2. `GET /api/search?q=K&limit=5` → 断言 `resumes`/`jobs`/`optimizations` 三组分别命中或为空。
  3. 空关键词或超长 → 返回空/按约束处理。
- **预期**：分组正确；跳转路径 `resumes→/resumes`、`jobs→/jobs`、`optimizations→/history/{id}` 正确。
- **冲突检查**：搜索不应跨权返回他人数据（按 `user_id` 过滤）；三组数据互不串档。

### CFT-10 权限边界（越权与公开接口）
- **涉及**：认证 / 管理员 / 资源归属。
- **步骤**：
  1. 普通用户无 Token 调 `GET /api/resumes` → 401。
  2. 普通用户调 `GET /api/admin/users` → 401。
  3. 用户 A 用自己 Token 调 `GET /api/applications/{B的投递id}`（B 是另一用户）→ 404（按 `user_id` 过滤）。
  4. 匿名调公开接口：`GET /api/jobs/categories`、`/interview-tracks/options`、`/applications/options`、`/communications/options`、`GET /api/files/{key}`（需有效签名）→ 均 **无需 Bearer** 即可访问。
- **预期**：越权一律 401/404；公开接口无需登录。
- **冲突检查**：公开接口不得泄漏他人 PII（如 `options` 仅返回枚举，不含任何用户数据）。

### CFT-11 每日额度跨接口一致性
- **涉及**：单投 / 批量 共享 Redis `delivery:count:{user}:{date}`，上限 20。
- **步骤**：
  1. 清理额度键；查 `contact-hint` 得 `sent_today=0`。
  2. 单投 N 个岗位（email）→ 每成功 1 次额度 +1；查 `contact-hint.sent_today` 同步 +N。
  3. 继续批量投递至第 20 封 → 单投/批量均开始返回 **429**；断言 `sent_today` 不再增长。
  4. 次日（或重置键）→ 额度归零，可再投。
- **预期**：单投与批量共用同一计数器，不会出现「单投满而批量仍放行」的口径冲突。
- **冲突检查**：官网表单（form）与平台引导（guide）**不占**邮件额度（CFT-13），断言其投递后 `sent_today` 不变。

### CFT-12 防重复唯一约束跨接口
- **涉及**：单投 409 ↔ 批量 409 ↔ 撤回释放（CFT-05）。
- **步骤**：
  1. 单投 `J` 得 `A`。
  2. 再单投 `J` → **409**。
  3. 批量投递含 `J` → 该项 **409 跳过**（`skipped+1`）。
  4. 撤回 `A` → 单投 `J` 重新 **201**；批量含 `J` 也 **201**。
- **预期**：唯一约束在单投与批量两条路径表现一致；撤回后约束释放。
- **冲突检查**：批量中「已投跳过」不应误计为 `failed_quota`（额度未消耗）。

### CFT-13 通道决策优先级跨参数组合
- **涉及**：投递通道决策（guide > email > form > manual）+ PIPL。
- **步骤**（每个组合独立用例，注意额度/名单前置）：
  - a. `channel_hint=guide` 但 `consent_given=false` → **422**。
  - b. `recipient_email` 非空但 `consent_given=false` → **422**（email 不发送）。
  - c. 同时传 `recipient_email` + `apply_url` 且 `consent_given=true` → 走 **email**（优先级高于 form）。
  - d. 仅 `apply_url` + consent → **form**（不占邮件额度，断言 `sent_today` 不变）。
  - e. 仅 `channel_hint=guide` + consent → **guide**（不占邮件额度）。
  - f. 都不传 → **manual**（无需 consent）。
- **预期**：显式 guide 优先；email > form；manual 兜底；对外通道强制 PIPL。
- **冲突检查**：guide 通道虽传 `apply_url`，但必须 `channel_hint=guide` 才走 guide（否则按 email/form 自动决策），避免「误把引导当表单」。

### CFT-14 解析依赖一致性（未解析统一报错）
- **涉及**：优化 / 匹配 / ATS / 评分 / 分析 共享 `parsed_json` 契约。
- **步骤**：
  1. 上传简历 `R0` 但解析失败 / 未解析；岗位 `J0` 同理。
  2. 分别调 `POST /optimize`(R0,J0)、`/match`(R0,J0)、`/ats/check`(R0)、`/resume/{R0}/score`、`/analysis/resume`(R0) → 断言均返回统一业务错误（400「尚未解析」/`PARSE_BEFORE_OPTIMIZE` 或 404）。
  3. 解析正常后重跑 → 全部成功。
- **预期**：所有依赖解析的入口对「未解析」给出一致、可预期的错误，而非空结果或 500。
- **冲突检查**：`analysis`（纯规则）与 `optimize`（AI）对缺失字段的报错口径一致，便于前端统一提示。

### CFT-15 回收站跨模块一致性
- **涉及**：回收站（简历 / 岗位 / 优化）统一入口 `/recycle`。
- **步骤**：
  1. 将 1 份简历、1 个岗位、1 条优化记录分别移入回收站。
  2. 断言：`/recycle` 三类各自可见；常规列表（`/resumes`、`/jobs`、`/optimize`）均不再显示。
  3. 批量恢复 → 常规列表重新出现；硬删后不可见。
- **预期**：三类回收站行为一致（软删可恢复、硬删不可逆），互不串档。
- **冲突检查**：优化记录被删后，其导出/历史入口应 404（不能悬空引用）。

### CFT-16 求职时间线跨模块聚合一致性（P0）
- **涉及**：投递 × 投递事件 × 沟通消息 × 面试进度（四个模块的数据在同一视图聚合）。
- **步骤**：
  1. 对岗位 J 创建投递 A → 时间线首项为「提交投递」。
  2. 对 A 走邮件直投（或 dry-run）→ 断言 `delivery_events`（queued/sent…）按时序追加进时间线。
  3. 给 A 记一条沟通（`POST /api/communications` {application_id:A}）→ 出现在时间线，且沟通 Tab 列表同时可见（同一数据源，非复制）。
  4. 新增面试进度：一条 `job_image_id=J`（精确匹配）、一条仅 company+position 兜底匹配 → 两条均出现在时间线。
  5. 改动数据后重查：删除沟通 → 时间线同步减少；撤回投递 A → 时间线接口 404（投递为轴，轴消失）。
  6. 权限：用户 B 查 A 的时间线 → 404；兜底匹配的公司+职位面试记录属于用户 B 时不混入用户 A 的时间线。
- **预期**：时间线是纯只读聚合——任何单模块的增删改都实时、正确地反映在时间线中，不产生副本数据、不遗漏、不串档（跨用户零泄漏）。
- **冲突检查**：兜底匹配（company+position）不得把同名公司同职位**其它岗位**的面试记录误挂（job_image_id 精确匹配优先）；软删除的面试记录/沟通不出现在时间线。

### CFT-17 逐条确认 × 简历版本树联动（P0）
- **涉及**：简历优化 × 逐条确认 × 版本树（三模块数据流转）。
- **步骤**：
  1. 对简历 R 做岗位优化得记录 O → `GET /api/resumes/{R}/version-tree` 中 O 为一级 `optimized` 节点。
  2. 对 O 逐条确认（接受 2 条 / 拒绝 3 条）→ 生成确认版 C（`parent_record_id=O`）。
  3. 再查版本树：C 出现在 O 之下为 `refined` 节点，`refined_count` +1；O 的 `optimized_json` 与确认前完全一致（原结果不可变）。
  4. 将 C 移入回收站（trash）→ 版本树中 C 消失（软删除不入树）、`refined_count` 回落；从回收站恢复 → 重新出现。
- **预期**：确认版不是覆盖而是**新增版本节点**，与 refine 微调同构进入版本谱系；任何单模块的删除/恢复在版本树实时反映。
- **冲突检查**：确认版不继承源记录的 `pdf_url`（旧 PDF 不张冠李戴，需重新导出）；确认版的 `match_score` 沿用源记录（口径一致，不虚报提升）。

### 6.2 执行建议
- **接口回归**：优先跑单功能用例（SF）打通各模块，再跑跨功能用例（CFT）验证端到端。
- **额度/约束**：CFT-11/12 每轮需清理 Redis 约束键（见 2.4），否则级联失败。
- **dry-run**：邮件相关用例在 SMTP/IMAP 未配置时仍可验证主流程与数据落库，仅需把「真实出网」预期改为「dry-run 事件落库」。
- **幂等**：CFT-03 的 `email/sync` 去重、CFT-12 的防重复均为幂等设计，重复执行不产生脏数据。
