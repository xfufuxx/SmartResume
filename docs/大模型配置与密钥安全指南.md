## 1. 先看清约束：项目的模型调用架构

### 1.1 调用链

项目**没有统一的 LLM 客户端**，而是 **7 个服务各自持有一份**：

| 服务文件 | 用途 | 使用的模型变量 |
|---|---|---|
| `app/services/resume_parser.py` | 简历 PDF 解析（含视觉 OCR） | `LLM_MODEL_VISION` + `LLM_MODEL_TEXT` |
| `app/services/job_parser.py` | 岗位 JD 解析（含图片 JD） | `LLM_MODEL_VISION` + `LLM_MODEL_TEXT` |
| `app/services/image_layout_editor.py` | 版面块识别与改写 | `LLM_MODEL_VISION` |
| `app/services/text_optimizer.py` | 简历文案优化 | `LLM_MODEL_TEXT` |
| `app/services/agent_optimizer.py` | 生成修改说明 | `LLM_MODEL_TEXT` |
| `app/services/interview_prep.py` | 面试题生成 | `LLM_MODEL_TEXT` |
| `app/services/refine_handler.py` | 局部精修 | `LLM_MODEL_TEXT` |

每个文件都有形如以下的工厂函数（以 `resume_parser.py:14-17` 为例）：

```python
def _get_client() -> AsyncOpenAI:
    if not settings.LLM_API_KEY:
        raise ValueError("LLM_API_KEY is not configured")
    return AsyncOpenAI(api_key=settings.LLM_API_KEY, base_url=settings.LLM_API_BASE)
```

### 1.2 三条硬约束（选型必须满足）

**约束 1 —— 必须支持视觉（图像输入）。**
简历链路是 `PDF → 渲染成图 → 视觉模型识读`（`resume_parser.py:99-117` 的 `_ocr_page_with_vision`）。**纯文本模型无法跑通主流程**。

**约束 2 —— 必须 OpenAI 兼容。**
统一走 `client.chat.completions.create(...)`，图像以标准格式传入：

```python
content=[
    {"type": "text", "text": "请从这张简历图片中提取所有文字内容…"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}},
]
```

即需要支持 **`image_url` + base64 data URL** 这一形态（不是所有「多模态」接口都照抄 OpenAI 的字段名）。

**约束 3 —— 文本与视觉共用同一个 `LLM_API_BASE`。**
`_get_client()` 只读一个 `base_url`。这意味着 **文本模型与视觉模型必须来自同一个服务端点**。若想文本用 A 家、视觉用 B 家，只能选**聚合平台**（一个 base_url 挂多厂商模型），或改代码支持双 base_url。

### 1.3 依赖的其他 API 特性

| 特性 | 使用位置 | 是否硬依赖 |
|---|---|---|
| `response_format={"type":"json_object"}` | `agent_optimizer.py:61,92`、`image_layout_editor.py:160`、`interview_prep.py:103` | **否**。代码检测到不支持会自动去掉该参数重试（`_safe_chat_completion`，见 `resume_parser.py:20-39`） |
| `max_tokens` ≤ 8192 | `agent_optimizer.py:93`、`interview_prep.py:104` | 是。模型输出上限须 ≥ 8192 |
| `temperature` 0.2 / 0.6 | 各服务 | 是 |
| 基础重试 | 各 `_safe_chat_completion`：3 次 + 指数退避 | — |

> 结论：**JSON mode 不支持也能跑**（有降级），但**视觉能力与 8192 输出上限是硬要求**。

## 2. 推荐选用什么大模型

### 2.1 推荐方案

| 方案 | 文本模型 | 视觉模型 | 适用场景 | 说明 |
|---|---|---|---|---|
| **A. 保持现状（最省事）** | MiMo-V2.5 | MiMo-V2.5 | 不想动代码、要一个模型全包 | 小米全模态模型（310B MoE / 15B 激活，1M 上下文，MIT 许可，2026-04 发布）。单一模型同时覆盖文本与视觉，**符合约束 3，零改动** |
| **B. 成本优先（推荐）** | Qwen3.5-Plus 或 Qwen3.5-Flash | qwen3-vl 系列 | 上线后调用量大、要压成本 | 阿里云百炼平台。同一 base_url 同时提供文本与视觉模型，满足约束 3。文本侧 Flash 档约 ¥0.2/¥2（输入/输出，每百万 token） |
| **C. 视觉质量优先** | 豆包 Seed 系列 | 豆包 Seed 系列 | 简历版式复杂、扫描件质量差 | 豆包多模态积累深（抖音系视频/图像数据），但旗舰档约 ¥6/¥30，**成本显著更高** |
| **D. 长文档 / 高难推理** | Kimi K3 或 GLM-5.2 | Kimi K3 | 超长简历、复杂 JD 语义对齐 | Kimi K3 约 ¥20/¥100，属旗舰价位，按需 |

### 2.2 明确不推荐的做法

| 做法 | 原因 |
|---|---|
| **用 DeepSeek V4 当视觉模型** | 截至 2026 年中，DeepSeek 多模态不是重点，V4 以文本/代码为主。**可以拿它当 `LLM_MODEL_TEXT`（约 ¥1/¥2，性价比极高），但不能拿它当 `LLM_MODEL_VISION`** |
| 文本与视觉选了两家，却只配一个 `LLM_API_BASE` | 会直接调用失败或静默走错模型。必须用聚合平台或改代码 |
| 只看榜单不看「图像输入字段格式」 | 部分厂商的「多模态」是自研字段，不兼容 OpenAI 的 `image_url`，接入即报错 |
| 把 `max_tokens` 需求忽略 | 项目用到 8192，输出上限过低的模型会在生成长简历时被截断 |

| DeepSeek V4-Flash | 1 | 2 |
| DeepSeek V4-Pro | 3 | 6 |
| 通义千问 Qwen3.5-Plus | 0.8 | 4.8 |
| 通义千问 Qwen3.5-Flash | 0.2 | 2 |

**成本结构提示**：一次简历优化会触发**多次**模型调用（解析简历 + 解析岗位 + 文案优化 + 生成修改说明，视觉链路是**每页一次**）。多页扫描件简历的视觉调用是成本大头。**建议：文本侧尽量用便宜档，视觉侧保质量**——这也是推荐「聚合平台 / 百炼」的原因：能在同一个 base_url 下分别配。

### 2.4 落配置示例

**保持现状（MiMo-V2.5）** —— 无需改代码，`backend/.env`：



> 具体模型名请以平台「模型列表」为准，各平台命名会迭代。

### 3.2 读取链路（可自行验证）

```
backend/.env
  └─> app/config.py:50-52   class Config: env_file = ".env"
```

`app/config.py:55` 的 `settings = Settings()` 是**模块级实例化**——进程启动时读一次 `.env`，之后**不会重新读取文件**。改完 `.env` 不重启，读到的仍是旧值。

### 3.4 管理后台改不了模型密钥（已核实）

| 端点 | 能力 | 能否改密钥 |
|---|---|---|
| `GET /api/admin/models` | 列出模型 + 24h 调用统计 | — |
| `PUT /api/admin/models/{model_id}` | 只接受 `weight` / `rate_limit_per_minute` / `is_enabled` / `tier` | ❌ **不能** |

**另有一个「看起来能配、实际是死字段」的坑**，需要你知道：

- 数据表 `model_routing` 有 `api_key_encrypted` 列（`app/models/admin.py:58`）；
- 但**全项目对它零读取、零写入**（`grep -rn "api_key_encrypted" backend/app/` 仅命中该行定义）；

也就是说：**「后台可视化配模型」这条路的表结构与字段已经铺好了一半，缺的是写入端点 + 让 `_get_client()` 改走 `route_model()`**。目前不要指望从后台改密钥，只能改 `.env`。

## 4. 密钥安全与加密

### 4.1 本次已修复：`.env.example` 的真实密钥泄露

**问题**：`backend/.env.example` 里填的是**真实值**，而非占位符；且它**被 git 跟踪**（`git ls-files` 确认在版本控制内）。根因是 `backend/.gitignore` 的一条反向规则：

```gitignore
.env
.env.*
!.env.example      # ← 把 .env.example 从忽略中捞出
```

**本次改动**：将 `.env.example` 三个敏感变量改为占位符（仅 3 行）：

| 变量 | 改前 | 改后 |
|---|---|---|
| `SECRET_KEY` | 36 字符真实值 | `change-me-to-a-long-random-string` |
| `LLM_API_KEY` | 51 字符真实值 | `sk-your-llm-api-key-here` |
| `SMTP_PASSWORD` | 16 字符真实值 | `your-smtp-auth-code` |

`.env`（本地实际配置）**未改动**，其中真实值仍在，且已被 `.gitignore` 忽略。

> ⚠️ 另外发现：`backend/.env.example` 里 `LLM_MODEL_TEXT/VISION` 写的是 `mimo-v2.5-pro`，而 `.env` 实际用的是 `mimo-v2.5`（非 pro）。模板与实跑不一致，建议统一，避免误判。

### 4.2 必做：轮换已泄露的密钥（3 步）

密钥**已进入 git 历史**，仅改当前文件不足以消除风险——历史提交里仍有明文。必须按序处理：

**第 1 步：到各平台作废并重新签发**
- LLM 服务控制台：吊销旧 key，签发新 key
- QQ 邮箱：重新生成 SMTP 授权码
- 生成新的 `SECRET_KEY`（见 4.6，注意连带后果）

**第 2 步：写入 `backend/.env`（**不要**写进 `.env.example`）**
```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"   # 生成 SECRET_KEY
```

**第 3 步：清理 git 历史中的明文**
```bash
# 需要 git-filter-repo（或 BFG）。先备份仓库！
git filter-repo --path backend/.env.example --invert-paths --force
# 或仅替换该文件内容：
git filter-repo --replace-text <(echo '旧密钥前缀==>REDACTED')
```
若仓库已推送到远端，清理后需 **force push 并通知所有协作者重新克隆**；同时按平台指引申请**清除远端缓存**（部分平台仍可从旧对象访问）。

> 判断是否真的泄露过：只要 git 历史里有，就当作**已泄露**处理，不要抱侥幸。

### 4.3 项目已有的加密能力（以及为什么它不适合直接存 API Key）

项目已实现 AES 加密：`app/core/crypto.py`，用于**简历原文 `raw_text` 落库加密**（`app/api/resumes.py:83` 写入加密、`:31` 读取解密）。

**实现方式**：
- 算法：**AES-256-CBC**
- 密钥：`_ENCRYPTION_KEY = sha256(SECRET_KEY)`（`crypto.py:13`）
- IV：随机 16 字节，**前置拼在密文前**（`crypto.py:17,24`）
- 输出：`base64(iv + ciphertext)`

**`SECRET_KEY` 目前是「一钥三用」**，改它会同时影响三处：

| 用途 | 位置 | 换 key 的后果 |
|---|---|---|
| JWT 签名（HS256） | `app/core/security.py:19,25,29,33` | **所有已签发 token 立即失效**，全员需重新登录 |
| AES 加密密钥派生 | `app/core/crypto.py:13` | **历史加密的 `raw_text` 永久无法解密**（简历内容丢失） |
| 文件签名 URL 的 HMAC | `app/services/storage.py:31,43` | 已下发的文件链接全部失效 |

**三点不足（若要拿它存 API Key，必须先补）**：

1. **无完整性校验**：CBC 模式没有 MAC/认证标签，密文可被篡改而解密不报错；正确做法是改用 **AES-GCM** 或加 HMAC（Encrypt-then-MAC）。
2. **密钥派生无拉伸**：直接 `sha256(SECRET_KEY)`，没有 salt / KDF 迭代。若 `SECRET_KEY` 熵不足，可被暴力破解。至少应使用 **HKDF** 分离出独立的加密密钥。
3. **解密未校验 padding**：`crypto.py:34` 直接 `pad_len = padded[-1]` 后切片，未验证合法性，篡改数据时可能静默截断或抛异常——若异常信息外泄存在 padding oracle 风险。

> 因此：**不要**为了「加密存 API Key」就直接复用 `encrypt_field()` 把它写进数据库——除非按上述三点加固，且主密钥不与密文同机存放。

### 4.4 API Key 的保管：四层方案

| 层级 | 做法 | 适用 |
|---|---|---|
| **L1 最低要求** | 只放 `backend/.env`，并确保 `.env` 在 `.gitignore`（**已满足**）；`.env.example` 只留占位符（**本次已修**） | 本地开发 |
| **L2 推荐** | **环境变量注入**，密钥不落盘：Docker `--env-file` / `docker secret`、K8s `Secret`、systemd `EnvironmentFile`、云平台环境变量配置 | 生产（多数团队够用） |
| **L3 落库加密** | 若确实要在后台配置多模型，启用 `model_routing.api_key_encrypted` + 加固后的加密函数。**前提**：主密钥放环境变量或 KMS，**不得**与数据库同机同文件 | 多模型可运营场景 |
| **L4 最佳** | **AI 网关**：应用只持有网关 token，真实上游密钥由网关保管与轮换；或直接上云 KMS / Vault 托管 | 有合规要求、多厂商多密钥 |

**L4 的额外好处**：本项目的 `LLM_API_BASE` 只需要改成一个网关地址，**代码零改动**——网关后面挂哪家模型、怎么轮换密钥，应用都不用知道。这是当前架构下升级成本最低的高安全方案。

### 4.5 日志脱敏缺口（建议补）

`app/core/log_filter.py` 只脱敏**手机号**与**邮箱**（`:9-10` 两条正则），**不覆盖 API Key、Bearer token、密码**。

风险点：`app/services/job_parser.py:96`、`resume_parser.py:159` 等位置会把上游错误原文拼进消息：

```python
f"LLM API Key 无效或已过期…原始错误: {e}"
```

部分 SDK 的异常字符串会带上请求头。**建议在 `log_filter.py` 增加两条规则**：

```python
_APIKEY_RE = re.compile(r"(sk-|tp-|Bearer\s+)[A-Za-z0-9_\-]{16,}")
_PWD_RE    = re.compile(r"(password|passwd|授权码)\s*[=:]\s*\S+", re.I)
```

### 4.6 更换 `SECRET_KEY` 的正确姿势

因为 4.3 的「一钥三用」，**不要直接改**，否则简历正文会解不开。建议顺序：

1. **先备份数据库**（尤其 `resumes.raw_text` 列）；
2. 用**旧 key 批量解密** → 用**新 key 重新加密**（写一次性迁移脚本）；
3. 确认迁移成功后，再替换 `SECRET_KEY` 并重启；
4. 通知所有用户**重新登录**（旧 token 全部失效）；
5. 已下发的文件签名 URL 会失效，属预期行为（前端会重新请求）。

### A.1 三条接入参数（官方文档原值）

| 项 | 值 |
|---|---|
| Base URL（OpenAI 兼容） | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| API Key 获取地址 | <https://platform.qianwenai.com/home/api-keys> |

### A.2 ★ API Key 填在哪里

**唯一位置：`backend/.env` 中的 `LLM_API_KEY` 一行。**

```ini
# backend/.env
LLM_API_KEY=sk-ws-你的真实Key
```

完整替换步骤：

1. 打开 <https://platform.qianwenai.com/home/api-keys> → **创建 API Key** → 填描述 → **生成**
2. **立刻复制**（完整 Key 只显示这一次，之后再看到的就是掩码版）
3. 打开 `backend/.env`，把 `LLM_API_KEY=` 后面替换成刚复制的 Key
4. **重启后端进程**（`settings` 是模块级单例，启动时只读一次 `.env`，不重启不生效）
5. 跑一遍自检：`cd backend && .venv/Scripts/python.exe verify_qwen_api.py`

三个容易搞错的点：

- **变量名是 `LLM_API_KEY`，不是 `DASHSCOPE_API_KEY`。** 官方文档示例里用后者，本项目统一用前者；写错名字不会报错，只会静默读不到 Key。
- **不要写在 `backend/.env.example` 里。** 那个文件被 git 跟踪，会被提交出去。
- **不要在管理后台找入口。** `PUT /api/admin/models/{id}` 只接受 weight / rate_limit / is_enabled / tier，改不了密钥（详见 3.4）。

### A.6 连通性自检

```bash
cd backend
.venv/Scripts/python.exe verify_qwen_api.py              # 文本 + 视觉
.venv/Scripts/python.exe verify_qwen_api.py --text-only  # 只测文本，省一次视觉费用
.venv/Scripts/python.exe verify_qwen_api.py --image ../岗位.png
```

脚本会依次校验：base_url 非空 → Key 非占位符 → 文本模型调用 → 视觉模型调用（用样例图）。
全通过会打印「全部通过 ✓」；失败会给出 401 / 404 / 模型不支持视觉 的分类排查提示。

**本次实测记录（2026-09-16）**：

- `GET https://dashscope.aliyuncs.com/compatible-mode/v1/models`（不带 Key）→ `HTTP 401`
  `{"error":{"message":"You didn't provide an API key. ..."}}` → 端点在线且为 OpenAI 兼容格式
- 用假 Key 调 `chat.completions` → `401 invalid_api_key` → **请求格式与 base_url 均正确**，只差有效 Key
- 填入占位符后跑自检 → 正确识别为「仍是占位符」并指出填写位置 → 脚本逻辑无误

### A.7 JSON mode 说明

业务代码调用时带 `response_format={"type": "json_object"}`，并在报错时自动去掉该参数重试
（`app/services/resume_parser.py:31-33`）。即使某个千问模型不支持 JSON mode，
也会自动降级，不会中断链路。
