## 一、P0 问题（正确性，必须先修）

### 问题 1：模板选择未持久化到简历记录

**现状（代码定位）**
- `backend/app/models/optimized_resume.py`：无 `template` 列。
- `backend/app/api/optimization.py:101-108`（同步创建）与 `:940-947`（异步任务创建）：均不写模板。
- `frontend/src/app/page.tsx:98`：`selectedTemplate` 纯 React state；`history/[id]/page.tsx:169`：`useState(DEFAULT_TEMPLATE)`，不读记录。
- `POST /{opt_id}/reexport?template=`：模板由调用方每次传入，服务端不记忆。

**理由**：规格模式 3 明确「用户选定的模板 ID 保存在简历记录的 `template` 字段（入库）……导出 PDF 时从数据库读取该字段并据此分发渲染器——这是『导出 PDF 带有准确模板信息』的根本保障，绝不允许导出链路自行猜测或写死模板」。当前实现把「唯一事实来源」放在了前端易失状态里。

**影响**：
1. 刷新页面 / 换设备 / 重开详情页后，模板选择丢失，重新导出静默变成默认「专业分栏」——用户视角是「我选的模板没生效」；
2. 服务端无法自证导出用了哪个模板，排查线上「PDF 版式不对」工单时缺少落库证据；
3. 后续画廊页「一键应用」、主题联动（问题 6）都依赖这个字段，不修则下游全部空转。

**方案（可落地步骤）**
1. `OptimizedResume` 增加 `template: Mapped[str] = mapped_column(String(50), nullable=True)`；
2. `db_migrations.py::MIGRATIONS` 登记 `("optimized_resumes", "template", "VARCHAR(50)")`（沿用现有幂等 ALTER 机制，老库启动自动补列）；
3. 两条创建路径写入模板（先过白名单，非法值走问题 3 的统一 resolve + warning）；
4. 新增 `PUT /api/optimize/{id}/template`：切模板 = 更新该字段（规格原话），可选带 `reexport=true` 热导出；
5. `_to_response` 下发 `template`；前端 history 页从记录初始化 state；reexport 的 `template` 参数改为**可选**，缺省读记录值（保持旧调用方兼容）；
6. 存量数据回填 `professional`（一次性 SQL 或启动迁移里 `UPDATE ... WHERE template IS NULL`）。

### 问题 2：同步优化端点丢弃用户模板选择

**现状（代码定位）**
- `backend/app/api/optimization.py:920`（`_run_optimize_task`）：`_generate_styled_or_fallback(..., template)` ✅ 传了；
- `backend/app/api/optimization.py:97`（`optimize()` 同步端点）：`_generate_styled_or_fallback(resume, optimized, job.parsed_job_json, body.custom_instructions)` ❌ 漏传 `body.template`。

**理由**：`pdf_styler.py:41-44` 已实现「用户指定 Jinja2 风格模板 → 直接渲染」，但同步端点不传，导致上传 PDF 简历时走 PyMuPDF 原样保留链，用户选的 `jade-classic` 被完全忽略。

**影响**：同一前端操作走异步路径（当前实际路径）结果正确，但任何直接调 `POST /api/optimize/` 的调用方（含未来的管理端/脚本）拿到的是「原样式 PDF」而非「所选模板 PDF」——两条路径行为不一致，是典型的埋雷代码。

**方案**：`:97` 补传 `body.template`；并把「用户显式选择风格模板时优先」在 `_generate_styled_or_fallback` 文档字符串中显式声明（现状 `if template and resume is not None` 的分支容易让后人误删）。

### 问题 3：非法模板 ID 静默回退，无告警日志

**现状（代码定位）**
- `optimization.py:540-541`：`if template not in _ALLOWED_TEMPLATES: template = "professional"`——无任何日志；
- `pdf_styler.py:75-77`：有 `logger.info` 但级别不够（info 会被常规流量淹没）；
- `pdf_generator.py`：完全不校验模板名，且 `_ensure_template()`（:110-114）在文件缺失时**把内置默认模板内容写到磁盘上再渲染**——拼错模板名会「自愈」成一个看似成功的错误产物。

**理由**：规格模式 2 要求「兜底必须显式：回退到默认模板的同时必须输出 warning 日志，绝不静默渲染错误模板」；验收 #7 要求可诊断性。

**影响**：线上出现「导出永远是默认模板」时，日志里只有一条 info 甚至没有痕迹，排查成本极高；`_ensure_template` 的写盘行为在只读容器文件系统（ECS 部署场景）下还会直接抛异常。

**方案**：
1. 新增统一帮助函数 `app/services/template_meta.py::resolve_template_id(template, default="professional") -> str`：非法值 → `logger.warning(f"[模板] 未注册的模板 ID {template!r}，回退默认模板 {default}")`；
2. API 边界（reexport / test-template / optimize 请求体）对非法值 **fast-fail 返回 400**，把「猜测」限制在服务端内部；
3. `_ensure_template` 移除运行期写盘，改为文件缺失即抛 `FileNotFoundError`（模板是随代码发布物，缺失=部署事故，应该炸响而不是静默自愈）。

## 二、P1 问题（架构与扩展性，规格核心模式未完全落地）

### 问题 4：元数据双事实源，无自动一致性校验

**现状**：`frontend/src/lib/template-registry.tsx`（14 条 TS 注册）与 `backend/app/services/template_meta.py`（14 条 Python 注册）字段一一对应但**完全手工同步**；外加 `_ALLOWED_TEMPLATES`、`JINJA2_STYLE_TEMPLATES`、`templates/*.html` 文件集、E2E 预期清单，共 6 处。规格全局约束 3 要求「建议写一个单元测试自动校验三处模板集合一致」——目前只有重量的 E2E（需起浏览器+双服务）。

**理由**：手工同步是漂移的温床。本次升级已同步 14 条，但没有任何机制阻止第 15 个模板只加一半。

**影响**：漏同步的典型事故——前端有卡片、后端 404 预览；或后端能渲染、前端选不到；或白名单漏了导致静默回退（问题 3）。

**方案**（两步走）：
1. **立即做**：新增 `scripts/check_template_sync.py`（纯文件解析 + 集合比对，秒级运行，可挂 pre-commit / CI）：
   - 解析 `template-registry.tsx` 的 `id:` 集合 vs `TEMPLATE_META` 键集 vs `templates/*.html` 文件名集 vs 两处白名单——四者必须相等；
   - 每个 registry 条目字段完备性（version 匹配 `^\d+\.\d+\.\d+$`、category 合法、react 模式必须有 lazyComponent）；
   - 每个模板 HTML 必须含 `@page` / `break-inside` / `print-color-adjust`（顺带覆盖问题 9）。
2. **中期做**：后端成为唯一事实源——`/api/templates` 已有列表端点，前端 registry 启动时水合（附构建期内置 fallback 防网络失败），彻底消灭双登记。

### 问题 5：版式特征元数据缺失，打印 CSS 无法「特征驱动」

**现状**：JadeAI 模式 1 的核心是 `BACKGROUND_TEMPLATES` / `TWO_COLUMN_TEMPLATES` 这类**结构化版式特征**（是否全幅背景头、是否双栏、侧栏宽度与深浅）。本项目 `TemplateMetadata.layout` 只有 `'dual'|'single'|'banner'|'dark'` 四值且语义混乱——`dark` 既是布局值又是配色描述；`violet`（深紫侧栏双栏）和 `professional`（普通双栏）都标 `dual`，消费方无法区分「要不要 `@page margin: 0`」「侧栏多宽」「深色侧栏跨页要不要背景延续」。12 个模板 HTML 各自硬编码 `@page`（`professional/simple` 还是 1.5cm 通用边距）。

**理由**：规格二-5 的整条打印分页规则（全幅背景 → margin 0；深色侧栏跨页背景延续；双栏侧栏宽度）都要求「按模板特征注入」；模式 1 要求特征数据「同时被画廊的分类与渲染、导出时的分页 CSS 决策两处消费」。

**影响**：新模板（jade 两套）靠人工在 HTML 里写对了规则，但老模板不会自动获得；每加一个模板，打印规则都要重新人肉实现一遍，漏一个规则就是一个 PDF 瑕疵。

**方案**：
1. `TemplateMetadata`（前后端同步）增加结构化特征：
   ```ts
   layoutFeatures: {
     fullBleedHeader: boolean   // 全幅背景头部 → @page margin: 0
     darkBackground: boolean    // 整页深色 → printBackground 必须 + box-decoration-break
     sidebar: null | { side: 'left' | 'right'; widthMm: number; dark: boolean }
     twoColumn: boolean
     timeline: boolean          // 时间轴条目（连线跨页处理）
   }
   ```
2. 新增 `backend/app/services/print_css.py::build_print_css(features, theme) -> str`：按特征生成 `@page` 边距策略、`break-inside: avoid` 条目级规则、`h2 { break-after: avoid }`、`orphans/widows`、深色侧栏 `box-decoration-break: clone` + body 渐变延续；
3. 模板 HTML 收敛为「打印 CSS 基座（问题 9）+ 模板私有视觉样式」两层，特征数据驱动基座参数。

### 问题 6：主题配置（themeConfig）链路缺失

**现状**：全项目无用户级主题配置。registry 的 `theme` 是模板固有色（只用于预览卡片取色），不可被用户修改；没有 `buildExportThemeCSS` 等价物。

**理由**：规格模式 4 要求「导出时合并主题配置 `{...DEFAULT_THEME, ...resume.themeConfig}`……预览与导出必须消费同一套主题变量，保证两边观感一致」；验收 #6 逐条列出主色/字体/字号/行距/页边距联动。

**影响**：验收 #6 完全无法满足；用户只能换模板不能改色，产品竞争力缺口。

**方案**（较大，建议独立排期）：
1. 数据层：`optimized_resumes` 增加 `theme_config JSONB`（或内嵌 `optimized_json.theme`，前者更干净）；
2. 定义 `ResumeTheme { primary, accent, fontFamily, baseFontSizePt, lineHeight, marginMm, sectionGapMm }`，与 `DEFAULT_THEME` 合并校验；
3. 后端 `build_export_theme_css(theme, template_id)` 生成 CSS 自定义属性（`--tpl-primary` 等）注入导出 HTML；模板私有样式改为消费变量；
4. 前端选择器新增「主题定制」抽屉（取色器 + 字体 + 边距滑块），预览组件同步消费同一份 theme；
5. PDF 元数据追加主题摘要（可选）。

### 问题 7：无独立模板画廊页

**现状**：规格任务 2 要求独立画廊页（分类分组浏览 + 固定示例数据实时预览 + 弹窗放大 + 「使用此模板」写入记录并跳回编辑器）。当前只有优化页/详情页内的 Modal 选择器，功能上覆盖了「分类/预览/一键应用」的 80%，但缺独立入口与「写入当前记录」的闭环。

**理由**：画廊是模板体系的「橱窗」，独立页可分享、可 SEO、可作为新用户着陆点；且「使用此模板」的写库闭环依赖问题 1 的 `template` 字段。

**影响**：功能缺口（验收 #3）；用户从其他地方（分享链接）进来没有模板浏览入口。

**方案**：新增 `frontend/src/app/templates/page.tsx`：复用 `TemplateRegistry` + iframe 真实排版 + React 组件预览双模式；「使用此模板」→ 有当前优化记录时 `PUT /{id}/template` 后跳转编辑器，无记录时作为新建初始模板；导航栏增加入口。

## 三、P1/P2 问题（性能）

### 问题 8：每次 PDF 导出冷启动一个 Chromium

**现状**：`resume_renderer.py::html_to_pdf_async` 每次调用都 `chromium.launch()`（headless，约 1-2s/次），渲染完即 `close()`。批量优化（batch-optimize 最多 5 个任务）、用户连续重新导出、E2E 全量跑时，启动成本被反复支付。

**理由**：Playwright 的 browser 实例是可复用资源；launch 是纯开销。

**影响**：单次导出延迟 +1-2s；高并发时 CPU/内存峰值；ECS 低配实例上体感明显。

**方案**：
1. FastAPI lifespan 内 `async_playwright().start()` 单例 + browser 常驻，请求级 `browser.new_context()`（隔离 cookie/缓存），关闭时收尾；
2. 或轻量池：`asyncio.Semaphore(2~3)` 限并发 + 空闲 context 回收；
3. 注意保留 Windows 上 sync API 的特殊处理（现状注释已说明，勿回归）。

### 问题 10：预览端点无缓存 + iframe 无懒加载

**现状**：`GET /api/templates/{key}/preview` 每次全量 Jinja 渲染 + `Cache-Control: no-store`；选择器弹窗内多个 css 模板同时打开 iframe 时会并发请求多个预览。

**方案**：以「模板文件 mtime + 模板 version」为 ETag，允许 `max-age=300` 私有缓存（模板变更即自然失效）；前端 iframe 加 `loading="lazy"` / 进入视口再加载；列表端点 `/api/templates` 加长缓存（元数据随版本发布，变化极低）。

## 四、P2 问题（安全性）

### 问题 11：SECRET_KEY 一钥三用 + 默认值

**现状**：`config.py:18` 默认值 `"change-me-in-production"`；该 key 同时用于 JWT 签名（`core/security.py`）与 AES-256 字段加密密钥派生（`core/crypto.py:13` `sha256(SECRET_KEY)`）。

**理由**：密钥混用违反职责分离——JWT 泄露面（token 日志、前端可见）与加密密钥泄露面不同；默认值意味着「忘改配置 = 生产裸奔」，且攻击者可对默认密钥预计算。

**影响**：任一用途的密钥 material 泄露波及其它用途；无法单独轮换。

**方案**：
1. 拆分 `JWT_SECRET` / `FIELD_ENCRYPTION_KEY` 两个独立配置；
2. 启动时校验：`APP_ENV=production` 且任一为默认值 → 拒绝启动（fail fast，ECS 部署时立刻暴露）；
3. 轮换支持：加密值加 `v1:` 版本前缀，解密时按前缀选密钥（多密钥窗口期并存）。

### 问题 12：AES-CBC 无完整性校验

**现状**：`crypto.py` 用 AES-256-CBC 手工 PKCS#7 padding，无 MAC；`decrypt_field` 对损坏/篡改密文直接抛异常（上层 500），且 CBC 比特翻转可被利用篡改明文（如把密存的身份字段改掉）。

**方案**：改用 `AESGCM`（`cryptography` 库 AEAD，nonce 随机、认证标签防篡改）或 Encrypt-then-MAC（HMAC-SHA256 over iv+ciphertext）；解密失败统一返回 `None` + 审计日志，不向客户端暴露细节。迁移策略：新旧格式双读（`v1:` CBC 兼容读、GCM 写），后台任务批量重加密。

### 问题 13：test-template 端点生产暴露面

**现状**：`optimization.py:1420-1446` `POST /api/optimize/test-template` 任意登录用户可触发全模板 PDF 渲染（每个 1-2s Chromium），注释已自标「上线前应改为 admin 鉴权或下线」。

**方案**：`APP_ENV=production` 时 404（或 admin 限定）；加基于用户维度渲染限流（复用现有 `_optimize_limiter` 的 Redis 计数模式，如 10 次/分钟）。

## 十一、问题 6 修复记录（2026-10-22 已落地：主题配置全链路）

### 11.1 方案选型：变量化而非覆盖层

规格模式 4 要求「预览与导出消费同一套主题变量」。两条路线：

- **覆盖层**（注入 `h2 { color: ... }` 之类规则）：需要为每套模板维护选择器映射，
  14 套模板的章节标题选择器各不相同（h2 / .content h3 / .section-title / .main-title），
  漏一套就是静默不生效；
- **变量化**（本次采用）：模板私有样式里的硬编码值机械替换为
  `var(--tpl-primary, <原值>)`，用户主题只改 `:root` 里的变量值。**无用户主题时
  回退值保证渲染与改造前逐像素一致**（verify_print_base 42/42 守护），且新增模板
  只要沿用同一约定就自动获得主题能力，零额外同步点。

### 13.2 缓存正确性设计（为什么不会 serving 旧版）

预览响应是**纯函数**：`render_template_html(模板文件, 固定演示数据, 主题参数)`，无时钟、无随机、无用户态。ETag 五元组覆盖了全部输入：

1. **模板文件 mtime**（`templates/{id}.html`）——改模板即失效；
2. **模板 version**（`TEMPLATE_META`）——元数据升版即失效；
3. **演示数据指纹**（`_DEMO_RESUME` 内容 SHA-256）——改演示数据即失效；
4. **主题参数**（规范化 JSON）——每个主题组合独立缓存，回拖滑块即时命中；
5. **渲染链代码 mtime**（`pdf_generator.py` / `print_css.py` / `resume_theme.py`）——改渲染逻辑即失效（否则开发者改完打印基座，浏览器 5 分钟内的旧预览仍是旧规则，属于「假 bug」来源）。

缓存策略选 `private` 而非 `public`：预览 HTML 虽为公开数据，但经 Next rewrites 代理且不带用户态，`private` 明确禁止共享缓存（CDN/代理）存储，最稳妥。

- 失效链实测：`touch` 模板文件 / `print_css.py` → ETag 立即变化（缓存自然失效）；
- 确定性：两次 200 响应体逐字节一致（`cmp`）；
- 代理链路：`:3000` rewrites → `:8000`，ETag/Cache-Control 透传无损；

## 十五、前端控制台告警清零（2026-10-22 已落地）

`verify_optimize_ui.py` 长期停在 23/24，唯一红项是「无本功能相关控制台错误」，明细里是三条 antd 告警。本轮逐条治本：

| 告警 | 出现阶段 | 根因 | 处理 |
|---|---|---|---|
| `[antd: message] Static function can not consume context like dynamic theme` | 登录、选择简历 | 静态方法脱离 React 树，拿不到 ConfigProvider 的动态主题（本项目有暗色主题，等于提示气泡始终是浅色） | `app/layout.tsx` 两处：模块顶层 `ConfigProvider.config({ holderRender: (node) => <App>{node}</App> })` + ThemedConfig 内 `ConfigProvider.config({ theme })` 随主题登记 |
| `[antd: Spin] tip only work in nest or fullscreen pattern` | 优化页 | `<Spin tip>` 在无 children 的独立模式下渲染 | 7 处独立 Spin 补 nest 子节点（`<div style={{minHeight:1}}/>`） |
| `[antd: Modal] destroyOnClose is deprecated` | 优化页 | antd 5.25 起改名 | 13 处 `destroyOnClose` → `destroyOnHidden`（安装版本 5.29.3 支持） |

**为什么选 `holderRender` 而不是 `App.useApp()`**：全站 306 处 `message.*` 分布在 28 个文件，含 `lib/api.ts` 这类非组件代码；逐个改造成 `App.useApp()` 需改导入 + 改调用 + 处理非组件场景，回归面大而收益相同。`holderRender` 是 antd 官方为「静态方法 + 主题」提供的渲染器钩子，一处配置即可让静态节点跑在 `<App>` 上下文中。

**类型陷阱**：antd 5.29 的 `.d.ts` 里 `holderRender` 只出现在 `GlobalConfigProps`（即 `ConfigProvider.config` 的入参），**不在 `ConfigProviderProps`**；当 prop 传会 `TS2322: Property 'holderRender' does not exist`。运行时 `config-provider/index.js` 确实支持从 props 读，但正确写法是 `ConfigProvider.config({ holderRender })`。

**只配 `holderRender` 还不够（本轮实测暴露）**：`holderRender` 只解决「静态节点进入 `<App>` 上下文」，主题仍拿不到——静态方法的 holder 在 React 树外自己渲染一层 `ConfigProvider`，其 `theme` 取自 `ConfigProvider.config` 登记的**全局主题**，而项目一直只把主题当 prop 传给 `<ConfigProvider>`。结果：暗色模式下提示气泡依旧是白底黑字。补上第二半后修复：

```tsx
// ThemedConfig 内，随主题对象变化重新登记
React.useEffect(() => {
  ConfigProvider.config({ theme: antdThemeObj })
}, [antdThemeObj])
```

实测对比（`.ant-message-notice-content` 的 computed 样式）：修前暗色 `rgb(255,255,255)` 白底 / 黑字（与浅色完全相同）；修后暗色 `rgb(31,31,31)` 深底 / 白字，浅色保持 `rgb(255,255,255)` 白底 / 黑字。

**回归守护**：新增 `scripts/verify_antd_message_theme.py`（8 项），在暗/浅两种主题下各触发一次静态 `message.error`，断言背景与文字的亮度、两主题背景必须不同、且不出现静态方法告警。**负向实测**：注释掉上面那行 `ConfigProvider.config({ theme })` 后 5/8，恰好挂掉三条主题断言（且证明修复确实改变了渲染结果，不是空断言）。

**验证**：`verify_optimize_ui.py` **24/24**（控制台错误明细为「无」）；`verify_antd_message_theme.py` **8/8**（含负向实测）；`verify_template_gallery.py` 13/13（覆盖 PreviewModal 的 Spin 改动）、`verify_message_nav.py` 39/39 且「无 JS 错误」、`verify_job_hub_modules.py` 24/24；`tsc --noEmit` 0 错误。

第十二节留下的最后一条待办是 `git filter-repo` 清理历史密钥。本轮执行，原则是**先量化再动手**——重写历史不可逆，不能凭"可能有密钥"就开工。

### 16.1 先扫：到底泄露了什么

新增 `scripts/scan_history_secrets.py`（只读、输出脱敏，仅显示前 6 位）。它做两件事：

1. 用通用模式扫全历史：`sk-` 前缀、`AKID`/`LTAI`/`ghp_`、私钥头、带口令的 DSN、`*_SECRET/*_KEY/*_PASSWORD` 赋值式；
2. 把 `backend/.env` 里**当前真实密钥值**逐个在历史里精确匹配（历史里出现过即算泄露）。

首扫结论（18 提交）：

| 项 | 结果 |
|---|---|
| `backend/.env` 是否进过版本库 | **从未提交** |
| 当前 4 个真实密钥值是否出现在历史 | **0/4** |
| 通用模式命中 | 23 处，其中 **21 处是误报**（`api_key=settings.LLM_API_KEY` 这类代码引用、`new_password` 这类字段名、`LLM_API_KEY: Optional[str] = None` 这类类型声明） |
| 真泄露 | **2 处**：① `运行与完善.md` 里的 `SECRET_KEY=<43 位字面值>` ② 旧 `backend/.env.example` 里的 `SMTP_PASSWORD=<16 位授权码>` |

两处都已在后续提交中修复（文件删除 / 改为 `your-smtp-auth-code`），**但历史仍可达**——这正是要重写历史的原因。

### 16.2 再删：操作与保底

```bash
# ① 全量备份（含全部分支/标签），并 verify
git bundle create ../archive/SmartResume-pre-scrub-<ts>.bundle --all
git bundle verify ../archive/SmartResume-pre-scrub-<ts>.bundle

# ② 替换规则（只列真密钥，dev 默认值如 POSTGRES_PASSWORD=postgres / admin123 不动）
literal:<SECRET_KEY 字面值>==>***REMOVED-LEGACY-SECRET-KEY***
literal:<SMTP 授权码>==>***REMOVED-SMTP-AUTH-CODE***

# ③ 重写（filter-repo 会主动删除 origin 远端，防止误推）
git filter-repo --force --replace-text <rules-file>
```

规则里刻意**不**处理 `docker-compose.yml` 的 `POSTGRES_PASSWORD: postgres` 与 `migrate_v4.sql` 里的 `admin123`：前者是本地开发的公开默认值（清了会让 compose 直接起不来），后者是演示管理员口令且**当前代码/文档里仍然存在**——历史清理解决不了"现在还在用弱口令"的问题，那属于部署配置项，写在这里作为提醒。

### 16.4 遗留与说明

- **凭证轮换状态**：泄露的 SMTP 授权码在当前 `.env` 中已是新值（与泄露值不同），旧 `SECRET_KEY` 也在问题 11/12 的三密钥拆分中作废——**无需紧急轮换**。若日后再次出现历史泄露，先轮换凭证、再清历史（历史清理无法使已泄露的凭证失效）。
- **GitHub 侧残留**：force push 后旧提交在本仓库已不可达，但 GitHub 对已知 SHA 的悬空对象可能仍可访问，直到其内部 GC。若仓库曾公开且密钥当时有效，应按"已泄露"处理（轮换），必要时联系 GitHub Support 触发清理。
- **协作提示**：历史重写后所有提交 SHA 变化，其他克隆必须重新 `git clone`；本地旧分支无法直接 `git pull`。
- **工具留存**：`scripts/scan_history_secrets.py` 可随时复跑（提交前/发布前自查），输出不含完整密钥值。
