# 投递功能真实触达 HR——现状分析、可行方案与分阶段实施计划

> 版本 v1.0 ｜ 2026-09-20 ｜ 基于代码实况 + 2026-09 招聘平台开放生态调研

---

## 一、现有投递功能实现现状

### 1.1 已具备的能力

| 能力 | 实现位置 | 状态 |
|---|---|---|
| 投递数据模型 | `backend/app/models/application.py` → `applications` 表 | ✅ 含 `job_image_id / resume_id / applicant_name / email / phone / cover_letter / status` |
| 防重复投递 | `UniqueConstraint(user_id, job_image_id)` + 创建前 409 | ✅ 数据库级约束 |
| 状态机 | `submitted → viewed → interview → offer / rejected` | ✅ 但**由用户手动推进**，无外部信号驱动 |
| 一键投递交互 | `frontend/src/app/jobs/page.tsx` 弹窗（选简历+附言） | ✅ 姓名/邮箱/电话从 User 快照自动带出 |
| 简历附件产出 | `backend/app/api/export.py` → `/resume/{id}/docx` | ✅ 可导出 DOCX（可作邮件附件；PDF 导出待确认/补齐） |
| 沟通记录联动 | `communications` 表 + 面试追踪枢纽三 Tab | ✅ 投递记录与沟通时间线已打通 |

### 1.2 关键缺口：为什么现在无法"真实投递"

**核心事实：当前投递只是"站内模拟"。** 点击投递后，数据仅写入本地 `applications` 表，没有任何信息真正离开系统到达 HR。具体缺口四项：

1. **无外部触达通道**：没有邮件发送、表单提交或任何到企业侧的传输机制。HR 永远收不到。
2. **平台官方投递 API 不可得（决定性约束）**：经调研（2026-09），
   - BOSS直聘的 **BossHi 开放平台**面向企业客户/合作伙伴（小程序与企业协作身份），**与 zhipin.com 求职端数据无关**，不存在"替求职者投递"的公开接口；
   - 智联招聘、前程无忧的 API（简历拉取、状态回写）同样全部是**招聘方（企业 ATS 对接）视角**；
   - 社区逆向 zhipin.com wapi 的做法存在封号风控与法律/ToS 风险，**不能作为产品路线**。
3. **无投递对象标识**：`job_images` 的解析结果（`parsed_job_json`）只含岗位标题/公司/描述，**未提取 HR 邮箱或官网投递入口**。
4. **无回执机制**：`status` 的 `viewed` 等状态没有外部事件来源，纯手工标记，无法证明"已送达/被查看"。

## 二、可行实现方案：三通道混合架构

既然"直接调平台 API 投递"这条路在官方层面不存在，真实触达 HR 的可行路径是以下三条通道并行，按岗位类型自动路由：

### 通道 A：邮件直投（核心通道，MVP）

邮件是企业 HR 接收简历的**正式且普遍的通道**（前程无忧自身就支持"邮件模式按职位分配独立邮箱"收简历）。

**数据流：**
```
JD 图片/文本 → LLM 提取 hr_email（缺省时用户补录/跳过）
    → 用户授权确认（PIPL 告知弹窗）
    → 后端组装邮件：简历 DOCX/PDF 附件 + 附言 + 结构化申请摘要
    → SMTP / 邮件服务商 API（阿里云邮件推送 DirectMail / 腾讯云 SES）
    → HR 邮箱
    → 状态回执：SMTP 接受即 delivered；IMAP 收件箱轮询解析退信(bounce)/HR 自动回复 → 更新状态
```

**关键设计：**
- `applications` 表扩展：`channel`（email/form/platform）、`recipient_email`、`delivery_status`（queued/sent/delivered/bounced/failed）、`provider_message_id`
- 新增 `delivery_events` 表：记录每次发送/回执/退信事件，形成投递时间线（自然融入面试追踪枢纽）
- 发送队列：Redis + 后台任务（项目已有 Redis），限频防骚扰（如单账号 20 封/日）
- 失败重试与退信告警

### 通道 B：企业官网表单半自动投递（进阶）

对 JD 中含官网招聘链接（careers 页 / ATS 托管页如 Moka、北森、Greenhouse）的岗位：

- **半自动而非全自动**：后端解析目标表单结构 → 前端本地（Playwright/浏览器扩展形态）**预填**姓名/邮箱/电话/简历附件 → **用户亲眼确认后手动点提交**
- 不做无人值守批量提交：规避目标站点的 ToS/反爬冲突，也符合"用户主导"的合规姿态
- 提交结果由用户标记或页面回执探测，写入 `delivery_events`

### 通道 C：平台岗位引导流转（兜底，现已可做）

对 BOSS直聘/智联等平台内岗位（无公开投递 API）：

- 投递弹窗点击后生成「**一键准备包**」：目标岗位深链 + 简历纯文本一键复制 + 附言复制
- 用户跳转官方 App 完成最后一步"发送"，回到本应用一键标记"已投递"
- 把现状的"假投递"升级为"真流程、真记录"，体验对齐招聘软件，且零合规风险

### 未来路线（阶段 4+）

- **企业 ATS 直连**：Moka、北森、Greenhouse、Lever 等提供公开的候选人投递 API——若企业用户（HR 侧）使用本系统，可反向接入
- **招聘服务合作资质**：以公司主体与平台签合作协议后接入官方接口——个人项目阶段不展开，作为产品化路线图

## 三、整体架构与数据流转

```
┌─ 前端 ────────────────────────────────────────────┐
│ /jobs 一键投递弹窗（新增：授权确认 + 通道展示）      │
│ /interviews 投递记录 Tab（新增：投递时间线/回执状态）│
└──────────────┬────────────────────────────────────┘
               │ API
┌─ 后端 FastAPI ─▼──────────────────────────────────┐
│ applications API（扩展 channel/delivery 字段）      │
│ delivery_service（通道路由 A/B/C）                  │
│   ├─ email_sender（SMTP/DirectMail 适配器）         │
│   ├─ jd_contact_extractor（LLM 提取 hr_email）      │
│   └─ bounce_parser（IMAP 轮询解析退信/自动回复）     │
│ 任务队列：Redis + 定时任务（限频/重试/轮询）          │
└──────────────┬────────────────────────────────────┘
               │
   邮件服务商 → HR 邮箱   /   官网表单(用户本地确认)   /   平台深链
```

**数据结构增量：**
- `applications` 加列：`channel`、`recipient_email`、`delivery_status`、`sent_at`、`provider_message_id`
- 新表 `delivery_events`：`application_id / event_type(queued|sent|delivered|bounced|replied|failed) / payload / occurred_at`
- `parsed_job_json` 解析 schema 增加 `hr_email`、`apply_url`（官网投递入口）字段

## 四、隐私与合规要点（PIPL《个人信息保护法》）

1. **单独同意**：简历属敏感个人信息（联系方式、工作教育经历、求职意向）。每次真实投递前弹窗告知：接收方（公司/邮箱）、投递目的、投递内容范围，用户**逐次明示同意**，记录同意快照（时间+版本）。
2. **数据最小化**：邮件正文只含岗位所需字段，简历附件由用户选定，禁止附带无关数据。
3. **用户控制权**：投递可撤回（站内删除 + 提供"撤回告知邮件"模板）；支持个人数据导出与删除（对应现有硬删逻辑需补充告知义务说明）。
4. **第三方委托处理**：邮件服务商作为受托处理者，选境内合规服务商（阿里云/腾讯云），传输 TLS 加密；`SECRET_KEY` 一钥三用问题在上线前必须轮换（既有安全待办）。
5. **反骚扰与真实身份**：发件邮箱使用真实注册域名，附言中含用户署名与联系方式；限频（20 封/日/账号）+ 重复投递冷却期；尊重退信/拒收信号，进入 suppression 名单。
6. **自动化边界**：官网表单只做"用户确认后半自动"，不进行无人值守批量提交，规避《反不正当竞争》与平台 ToS 冲突。
7. **留存期限**：投递记录与简历附件设定保留策略（建议默认 2 年或用户注销即删），`delivery_events` 日志脱敏存储。

## 五、分阶段实施计划

### 阶段 0：现状基线（已完成 ✅）
站内模拟投递闭环、防重复、状态机、三模块边界——即当前代码状态。

### 阶段 1：邮件直投 MVP（通道 A）— 约 12~15 人日

| 任务 | 工作量 | 说明 |
|---|---|---|
| `parsed_job_json` 增加 `hr_email/apply_url` 提取（LLM prompt + 用户补录 UI） | 2 人日 | 提取失败时弹窗让用户填邮箱或转通道 C |
| `applications` 加列 + `delivery_events` 表 | 1 人日 | create_all 自动建表 |
| 邮件发送服务（SMTP 适配器 + 配置项） | 2 人日 | 先 SMTP 自有邮箱，后切 DirectMail |
| 简历 PDF 导出（补齐，现有仅 DOCX） | 2 人日 | 复用现有 export/浏览器打印方案 |
| 授权确认弹窗 + 同意记录 | 1.5 人日 | PIPL 告知文案 + 快照落库 |
| Redis 发送队列 + 限频 + 重试 | 2 人日 | 后台任务，失败可查 |
| 投递状态回写（sent/delivered/bounced 基础版） | 1.5 人日 | SMTP 响应 + 手动标记过渡 |
| 回归脚本 | 1.5 人日 | 扩展 `verify_job_hub_modules.py` |

**验收标准**：真实发送一封含简历附件的申请邮件到测试 HR 邮箱且可打开；重复投递被 409 拦截；未授权不发送；限频生效；投递状态在面试追踪枢纽可见。

### 阶段 2：投递追踪与回执闭环 — 约 8~10 人日

| 任务 | 工作量 |
|---|---|
| IMAP 轮询解析退信/HR 自动回复 → `delivery_events` | 3 人日 |
| 投递时间线 UI（融入面试追踪"投递记录" Tab） | 2.5 人日 |
| 邮件模板管理（默认模板 + 用户自定义附言模板） | 1.5 人日 |
| 批量投递（勾选多岗位排队，限频调度） | 2 人日 |
| 撤回告知邮件 + suppression 名单 | 1.5 人日 |

**验收标准**：退信自动标记 bounced 并告警；HR 自动回复出现在沟通时间线；批量投递不超限；撤回后收到告知邮件。

### 阶段 3：官网表单半自动投递（通道 B）— 约 12~15 人日

| 任务 | 工作量 |
|---|---|
| careers/ATS 页面解析（识别投递表单结构） | 4 人日 |
| 本地浏览器半自动填充（预填 + 用户确认提交） | 5 人日 |
| 合规评审（ToS/robots 核查清单） | 1 人日 |
| 提交结果回填 UI | 2 人日 |

**验收标准**：对 Moka 托管招聘页完成一次"预填→用户确认→提交成功→状态记录"全流程；无自动化绕过人工确认的行为。

### 阶段 4：平台引导包 + 企业侧合作（长期，约 4~6 人日 + 商务周期）

- 通道 C「一键准备包」（深链 + 简历文本复制）：4~6 人日，**零合规风险，可提前到阶段 1 顺带做**
- 企业 ATS 直连（Moka/Greenhouse）与平台商务合作：依赖公司主体资质与商务谈判，不在个人开发周期内排期

## 六、优先级建议

1. **立即做**：通道 C 一键准备包（1 周内可上线，把"假投递"变"真流程"）
2. **第一阶段主线**：通道 A 邮件直投 MVP——这是唯一能让"申请真实到达 HR"且完全合规的自动化通道
3. **谨慎推进**：通道 B 官网半自动；**坚决不做**：逆向平台 wapi 的模拟提交（封号 + 法律风险）
